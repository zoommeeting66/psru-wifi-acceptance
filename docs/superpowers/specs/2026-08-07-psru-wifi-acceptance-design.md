## 1. เป้าหมายและขอบเขต

### ปัญหาที่แก้
โครงการติดตั้ง Wi‑Fi 1,000 จุดต้องมีหลักฐานการตรวจรับครบทุกจุดก่อนคณะกรรมการลงนาม ปัจจุบันมีเพียงต้นแบบ HTML ไฟล์เดียวที่เก็บข้อมูลใน localStorage ของเบราว์เซอร์เครื่องเดียว ทำให้ช่างภาคสนามหลายทีมทำงานพร้อมกันไม่ได้ หลักฐานรูปถ่ายอยู่นอกระบบ และไม่มีร่องรอยว่าใครบันทึกอะไรเมื่อไร

### สิ่งที่ระบบนี้ทำ
รับผลตรวจจากช่างภาคสนามผ่านมือถือ (ทำงานได้แม้ไม่มีสัญญาณ) รวมศูนย์ไว้ที่ฐานข้อมูลเดียว ให้คณะกรรมการติดตามความคืบหน้า จัดการข้อบกพร่อง (NCR) และออกเอกสารสรุปเสนอลงนาม

### สิ่งที่ระบบนี้ **ไม่** ทำ
ระบบไม่ตัดสิน "ผ่าน / ไม่ผ่าน" การตรวจรับแทนคณะกรรมการ ระบบแสดงเพียง *ค่าที่วัดได้เทียบกับเกณฑ์ที่อ้างอิงจาก TOR/สัญญา* และชี้จุดที่ต่ำกว่าเกณฑ์ การตรวจรับตามกฎหมายเกิดจากการลงนามของคณะกรรมการเท่านั้น ข้อความนี้ต้องปรากฏบนหน้าจอหลักและในเอกสาร PDF ทุกฉบับ

### ขอบเขต v1
เข้าข่าย: ภาพรวม · จุดติดตั้ง · แผนตรวจ · ข้อบกพร่อง · รายงาน/ส่งออก · หน้าเก็บข้อมูลบนมือถือ · สรุป PDF เสนอกรรมการ

ไม่เข้าข่าย v1: หน้าจอจัดการผู้ใช้ · หน้าจอตั้งค่าเกณฑ์ TOR · แจ้งเตือน LINE/อีเมล · การเชื่อมต่อ controller ของ AP โดยตรง

## 3. โครงสร้างข้อมูล

### หลักการสำคัญ: ผลตรวจเป็นบันทึกแบบเพิ่มอย่างเดียว

การลงตรวจแต่ละรอบสร้าง `Inspection` **แถวใหม่เสมอ** ไม่แก้ทับของเดิม สถานะของจุดเป็นค่าที่ *คำนวณ* จาก "ผลตรวจล่าสุด + ข้อบกพร่องที่ยังเปิดอยู่" ไม่ใช่ค่าที่เก็บไว้แล้วแก้ไปมา

ผลที่ได้สามอย่าง:
1. ไม่มี write conflict ตอน sync จากมือถือ เพราะไม่มีใครเขียนทับใคร
2. ได้ audit trail ของการตรวจทุกรอบโดยไม่ต้องทำเพิ่ม ซึ่งเป็นสิ่งที่การตรวจรับต้องการอยู่แล้ว
3. การตรวจซ้ำหลังแก้ไข NCR เป็นเรื่องธรรมชาติ ไม่ใช่กรณีพิเศษ

### ตาราง

| ตาราง | ฟิลด์สำคัญ | หมายเหตุ |
|---|---|---|
| `User` | username, passwordHash, name, role | role: `FIELD` \| `COMMITTEE` \| `ADMIN` |
| `Project` | name, contractNo, torRef, totalPoints | โครงการเดียวใน v1 แต่เผื่อโครงสร้างไว้ |
| `Building` | code, name | |
| `Point` | code (AP‑0001), buildingId, floor, room, deviceModel, serial, mac | ทะเบียนจุดติดตั้ง |
| `Criteria` | key, label, operator, threshold, unit, torClause | เช่น `rssi` ≥ −67 dBm อ้างอิง TOR ข้อ … |
| `Inspection` | pointId, inspectorId, inspectedAt, measurements(Json), note, clientUuid, syncedAt | **append‑only**, `clientUuid` unique |
| `Evidence` | inspectionId, kind, filePath, mime, size, sha256, capturedAt | kind: LOCATION, LABEL, CONFIG, FUNCTIONAL, PERFORMANCE, DOCS |
| `Defect` | pointId, inspectionId, severity, title, detail, owner, dueDate, status, closingInspectionId | severity: `URGENT` \| `MAJOR` \| `MINOR` · status: `OPEN` \| `FIXED` \| `CLOSED` |
| `Plan` | date, team, note, gates(Json) | แผนลงพื้นที่รายวัน · `gates` เก็บสถานะ 4 ขั้นของวันนั้น (ตรวจเอกสาร / ตรวจหน้างาน / ทดสอบระบบ / สรุปผล) ค่าเป็น `PENDING` \| `ACTIVE` \| `DONE` หัวหน้าทีมเป็นผู้กด |
| `PlanItem` | planId, pointId, order, doneAt | |
| `AuditLog` | actorId, entity, entityId, action, payload(Json), at | |

### การคำนวณสถานะจุด (`services/pointStatus.ts`)

```
ไม่มี Inspection            → รอตรวจ
มี Defect status=OPEN       → มีข้อบกพร่อง
มี Defect status=FIXED      → รอตรวจซ้ำ
Inspection ล่าสุด: หลักฐาน 6 ประเภทครบ และไม่มีค่าที่ต่ำกว่าเกณฑ์ → หลักฐานครบ
นอกนั้น                     → รอตรวจสอบ
```

"หลักฐานครบ" หมายถึงข้อมูลขั้นต่ำครบเท่านั้น ไม่ใช่คำวินิจฉัยว่าผ่าน TOR — ข้อความกำกับนี้ต้องอยู่ติดกับตัวเลขบนหน้าจอ

### `clientUuid` — กุญแจของการทำงานออฟไลน์
มือถือสร้าง uuid ตั้งแต่ตอนเริ่มกรอกฟอร์ม server ทำ upsert ตาม uuid นี้ ยิงซ้ำกี่ครั้งก็ได้แถวเดียว ทำให้การส่งซ้ำเมื่อเน็ตหลุดกลางคันปลอดภัยโดยสมบูรณ์

### 4.2 หน้าจอเดสก์ท็อป (กรรมการ / เจ้าหน้าที่)

**ภาพรวม**
แถบเตือนสีครีมด้านบนแสดงข้อความว่าระบบไม่ตัดสินแทนคณะกรรมการ · KPI 4 ตัว (จุดทั้งหมด / ตรวจแล้ว / รอตรวจ / พบข้อบกพร่อง) · การ์ดแผนงานวันนี้พร้อมความคืบหน้า และแถบ Gate 1–4 ที่อ่านค่าจาก `Plan.gates` ของวันนั้น · รายการข้อบกพร่องคงค้างแยกตามระดับความเร่งด่วน · ตารางจุดที่มีความเคลื่อนไหวล่าสุด

**จุดติดตั้ง**
ทะเบียน 1,000 จุด ค้นหาด้วยรหัส/อาคาร/Serial/ผู้ตรวจ กรองตามอาคารและสถานะ **แบ่งหน้า 50 แถวพร้อมตัวเลขหน้า** — ต้นแบบเดิมตัดเหลือ 300 แถวแรกโดยไม่บอกผู้ใช้ ซึ่งซ่อนข้อมูลและอันตรายกับงานตรวจรับ คลิกจุดเปิดแผงด้านข้าง: ข้อมูลจุด, ประวัติการตรวจทุกรอบเรียงตามเวลา, รูปหลักฐานแต่ละรอบ, NCR ของจุดนั้น

**แผนตรวจ**
มุมมองรายวัน สร้างแผน: เลือกวันที่ → ทีม → เลือกจุด (เลือกทั้งอาคาร/ชั้นได้ในคลิกเดียว) → บันทึก จุดในแผนจะปรากฏบนมือถือของทีมนั้นทันทีที่ซิงก์

**ข้อบกพร่อง**
บอร์ดแยกตามระดับ (เร่งด่วน / สำคัญ / ทั่วไป) แต่ละใบแสดงจุด ผู้รับผิดชอบ กำหนดเสร็จ และอายุของ NCR
**การปิด NCR ต้องอ้างอิงผลตรวจซ้ำที่มีหลักฐานแนบ** ปิดด้วยการกดปุ่มเปล่า ๆ ไม่ได้

**รายงาน**
สรุปตามอาคารและสถานะ · ส่งออก CSV (คงความสามารถเดิมของต้นแบบ) · สร้าง PDF สรุปเสนอคณะกรรมการ

### 4.3 หน้าจอมือถือ (ช่างภาคสนาม) — `/m`

ไม่ใช่หน้าเดสก์ท็อปย่อส่วน แต่เป็นเส้นทางแยกที่ออกแบบให้ใช้นิ้วโป้งมือเดียว

1. **จุดวันนี้** — รายการจุดตามแผนของทีม พร้อมป้ายจำนวน "ค้างส่ง"
2. **ฟอร์มตรวจจุด** — หน้าเดียวจบ: Serial/MAC, ค่าที่วัดได้ (แสดงเกณฑ์ TOR กำกับใต้ช่อง), ช่องถ่ายรูปหลักฐาน 6 ช่องที่กดแล้วเปิดกล้องทันที, ช่องบันทึกข้อบกพร่อง, ปุ่มบันทึกใหญ่ท้ายจอ
3. กดบันทึก → เข้าคิวทันที ไม่รอเน็ต → กลับไปหน้ารายการ

แถบสถานะบนสุดแสดงตลอดว่าค้างส่งกี่รายการ ช่างต้องเห็นชัดว่างานยังไม่ถึงเซิร์ฟเวอร์

## 5. กลไกการทำงานออฟไลน์

- **Service Worker** แคชตัวแอป ฟอนต์ และรายการจุดในแผนวันนี้ เมื่อเปิดครั้งแรกที่ยังมีสัญญาณ
- **ย่อรูปในเครื่อง** เหลือด้านยาว 1600px คุณภาพ 0.8 ก่อนเข้าคิว เพื่อไม่ให้ IndexedDB บวมจนเบราว์เซอร์ล้างทิ้ง
- **คิวขาออก (outbox)** ใน IndexedDB เก็บทั้งข้อมูลฟอร์มและ blob รูป
- **ส่งอัตโนมัติ** เมื่อ event `online` ทำงาน และมีปุ่มส่งเองด้วย
- **ล้มเหลวแล้วถอยแบบ backoff** (10s → 30s → 2m → 10m) ไม่ลบรายการทิ้งเด็ดขาด
- **ไม่มี conflict resolution** เพราะทุกการส่งคือแถวใหม่ + upsert ตาม `clientUuid`

## 6. สิทธิ์การใช้งาน

JWT + bcrypt แบบเดียวกับ `expiry-notification-system`

| บทบาท | ทำได้ |

ไฟล์หลักฐานเสิร์ฟผ่าน route ที่ตรวจสิทธิ์ ไม่ใช่ static path เปิดโล่ง

## 8. การจัดการข้อผิดพลาด

- ตรวจ input ทุก endpoint ด้วย **zod** คืนข้อความภาษาไทยที่คนหน้างานอ่านเข้าใจ
- จำกัดขนาดไฟล์อัปโหลด (5MB/ไฟล์) และชนิดไฟล์ (jpeg/png/pdf)
- **Serial ซ้ำข้ามจุด → เตือน ไม่บล็อก** เพราะของจริงอาจพิมพ์ผิดหรือมีการสลับอุปกรณ์ การบล็อกจะทำให้ช่างติดอยู่กลางสนาม
- อัปโหลดจากคิวล้มเหลว → เก็บสาเหตุไว้ในรายการ แสดงให้ช่างเห็น ไม่หายเงียบ
- ดิสก์เต็ม / เขียนไฟล์ไม่ได้ → คืน 507 และคิวฝั่งมือถือจะ retry ไม่ทิ้งข้อมูล

## 9. การทดสอบ

เน้นจุดที่พังแล้วเจ็บ ไม่ไล่ทำ coverage ให้ครบทุกบรรทัด

1. **Idempotency** — ส่ง inspection เดิมด้วย `clientUuid` เดิม 3 ครั้ง ต้องได้แถวเดียว
2. **Replay คิวออฟไลน์** — คิวที่มี 5 รายการ ส่งขณะเน็ตล่ม 2 ครั้งแรก ต้องจบด้วยข้อมูลครบ 5 ไม่ซ้ำ
3. **การคำนวณสถานะจุด** — ทดสอบครบทุกสาขาของกฎในข้อ 3
4. **การเทียบเกณฑ์ TOR** — ค่าที่ขอบเกณฑ์พอดี (−67 dBm) ต้องไม่ถูกตีเป็นต่ำกว่าเกณฑ์
5. **RBAC** — `FIELD` เรียก endpoint ปิด NCR ต้องได้ 403
6. **PDF** — สร้างได้และมีข้อความภาษาไทยจริงในไฟล์ผลลัพธ์

---

## 10. การย้ายข้อมูลจากต้นแบบเดิม

ต้นแบบเดิมเก็บใน localStorage และมีปุ่มส่งออก CSV อยู่แล้ว จึงเตรียม script `scripts/importCsv.ts` รับ CSV รูปแบบเดิม (คอลัมน์ `AP_ID`, `อาคาร`, `ชั้น`, `พื้นที่`, `Serial`, `MAC`, `ผู้ตรวจ`, …) มาสร้าง Point และ Inspection ตั้งต้น เผื่อมีข้อมูลที่กรอกไว้แล้วในเครื่องใดเครื่องหนึ่ง

## 11. คำถามที่ยังต้องได้คำตอบก่อน/ระหว่างลงมือ

1. เกณฑ์ตัวเลขจริงจาก TOR/สัญญา (RSSI, ความเร็ว, จำนวนผู้ใช้พร้อมกัน) — ใช้ค่าตัวอย่าง RSSI ≥ −67 dBm ไปก่อน แล้วแก้ใน seed
2. รายชื่ออาคารและผังจุดจริง 1,000 จุด — ใช้ข้อมูลตัวอย่างรูปแบบเดียวกับต้นแบบเดิมไปก่อน
3. เซิร์ฟเวอร์ปลายทางที่จะ deploy และนโยบายสำรองข้อมูล

ทั้งสามข้อไม่บล็อกการพัฒนา เพราะเป็นข้อมูลตั้งต้น ไม่ใช่โครงสร้าง
